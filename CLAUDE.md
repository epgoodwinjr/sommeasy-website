# CLAUDE.md — Sommeasy

## What This Project Is

Sommeasy is a wine recommendation app that helps users find wines from restaurant menus matching their taste preferences. A user provides a restaurant menu (photo, PDF, URL, or pasted text), sets their taste preferences and budget, and Sommeasy recommends specific bottles from that menu — with personalized sommelier notes from The Somm.

This is the full Sommeasy web app — quiz, DNA profile, restaurant recommendation engine with LLM storytelling, wine journal, and bottle logging.

**Naming:** The Palate = the DNA profile system. The Somm = the matching/recommendation system (and its voice).

## Tech Stack

- **Framework:** Next.js 14 (App Router)
- **Auth + Database:** Supabase (Postgres with RLS, auth.users) — project `zugunlctgpytgyxftllv`; a daily Vercel cron hits `/api/keepalive` (09:00 UTC, proper server-side `createServerClient`) so the free-tier project never auto-pauses again (the March 2026 pause killed the original database). Custom SMTP (Resend) is live (auth email cap 30/hr); the browser `createClient` (`src/lib/supabase.js`) FAILS THE BUILD loudly if `NEXT_PUBLIC_SUPABASE_*` are missing — a green deploy with dead auth is impossible (verified: static `/` prerender throws)
- **Styling:** Inline styles / CSS-in-JS (no Tailwind)
- **PDF processing:** unpdf with Y-coordinate detection for line breaks
- **Claude model:** one constant — `CLAUDE_MODEL` in `src/lib/anthropicConfig.js` (default `claude-sonnet-4-6`, override with the `ANTHROPIC_MODEL` env var). Never hardcode a model ID in a route; a retired hardcoded ID silently killed prod scanning for three weeks in June 2026
- **Menu scanning:** Claude Vision via `/api/parse-wine-list` (photo/PDF/scraped text)
- **Bottle label OCR:** Claude Vision via `/api/scan-label` (tesseract.js was removed — it was a declared-but-never-called dependency)
- **Somm curation:** `/api/somm-picks` — one Claude call turning scored candidates into curated picks + notes
- **Deployment:** Vercel (auto-deploys from main)
- **Core flow:** Scan/URL/paste → structured wine data → DNA matching (with journal feedback signals) → algorithmic curated picks render instantly → The Somm re-curates with storytelling in the background

## Brand & Design

### Colors
- **Deep forest green** — primary
- **Burgundy** — accent
- **Sage** — secondary/supporting
- **Cream** — backgrounds and light surfaces

### Typography
- High-contrast serif typography
- The brand feels sophisticated but approachable — think "knowledgeable friend who knows wine," not "stuffy sommelier"

### Design Principles
- Clean, uncluttered layouts with generous whitespace
- Visual hierarchy should guide the eye naturally — don't rely on users reading everything
- Photography and imagery should feel warm, real, inviting (not stock-photo sterile)
- Mobile-first — most users will hit the site from phones. Form inputs stay ≥16px font (iOS auto-zoom) and tap targets ≥40px

## Voice & Tone

Sommeasy's voice is:
- **Confident but not pretentious** — we know wine, but we don't gatekeep
- **Warm and conversational** — like a friend giving you a recommendation
- **Clear and direct** — no jargon unless it genuinely helps

Bad: "Leveraging AI-powered algorithms to curate optimal wine pairings"
Good: "Tell us what you like. We'll find it on the menu."

Every error and empty state follows this voice: warm, no raw error strings, always tells the user what to do next.

## Key Technical Context

- PDF text extraction uses Y-coordinate detection (transform[5]) to preserve line breaks — naive extraction merges everything into one blob and breaks the parser
- Wine name cleanup handles: dot leaders, bin numbers, broken accent characters, section headers misidentified as wine entries, US state abbreviations
- **Unified data architecture:** Single `wineUnified.json` (built by `scripts/build_quiz_data.py` from 130k WineMag reviews) powers all engines — quiz, profile, match. Contains countries, regions, producers, varietals, plus regionLookup, producerLookup (9,135), and varietalLookup (31 synonym mappings)
- **Matching is word-boundary based, never raw substring.** Producers named "Cass"/"Pier"/"Rozès" used to match inside "Cassis"/"Pierre"/"Crozes-Hermitage" and misattribute countries. `termMatchesInText` (matchEngine) and `containsTerm` (wineResolver) enforce boundaries — including the possessive rule (Aug 2026): "X's ⟨site⟩" names a vineyard after a person, so `mate` never matches inside "Maté's" (a `(?!'s…)` lookahead; the apostrophe still bounds quoted names). Defense in depth: if a matched producer's country contradicts a country the wine name states outright (name or region term), `resolveWine` caps confidence at 55 — below `PARTIAL_CONFIDENCE_GATE` (60), not merely `CONFIDENCE_GATE` (80) — so a disputed match accumulates NOTHING: the partial band writes region/country points, and producer-derived region/country are exactly the dimensions a geography conflict disputes. The countryAttribution suite + dnaEvolution 10H guard all of this permanently
- **A producer hit is a guess; the line's own words outrank it** (Oct 2026). (1) **Core-name aliases** — `src/lib/producerAliases.js` builds ONE table from wineUnified for both engines: each producer is also indexed under the name menus write, its generic designators stripped from the ends ("Finca"/"Bodegas"/"Domaine"/"Château"… and "Vineyards"/"Winery"/"Wines"/"Estate"/"Cellars"), so specificity beats a shorter namesake ("newton johnson" > Napa's "newton", "la emperatriz" > Stellenbosch's "jardin"). Guardrails, each a real collision in the data with its own test: aliases match as WHOLE PHRASES only (the `wholePhrase` flag on `termMatchesInText`/`containsTerm` — multi-word terms otherwise match as plain substrings, and "lo alto" sits inside "Palo Alto"); two or more words (a one-word core is a new Jardín); never preposition-led after a stripped leading designator ("Cantina di Montalcino" → "di montalcino" would claim every Brunello; US "Casa de la Cruz"); never a core another producer shares or contains ("Meyer Family" US/Canada, "San Mauro" Italy/Spain); never inside a place or grape name ("Dry Creek Vineyard" vs Dry Creek Valley). (2) **The engine's namesake guard** (`detectWineAttributes`): a producer whose country contradicts the region or country the line names is discarded — no country, estate, quality or feedback signal. Geography inside the producer's own matched name ("Concha y Toro", "Vega Sicilia") states nothing, and a region name two countries share agrees with either (`sharedWith` on the region term — regionLookup maps "central valley" to California, but Chile has its own; read US-only, it vetoed every Chilean producer naming its home region, a regression the before/after corpus diff caught before ship). `producerTerms` carries the CANONICAL producerLookup key, so estate, feedback and producer-id lookups see one producer whether the menu wrote the full name, an "&" variant or the core. (3) **Combined region names** ("Hemel-en-Aarde / Walker Bay") are split into parts in both region indexes, like varietals — unsplit, the resolver's Step 3.5 cap couldn't see "Hemel-en-Aarde" and accumulated Santa Barbara's "Storm" at confidence 90
- **The resolver's place-word rules** (`wineResolver.js`, Oct 30, 2026): `resolveWine` lists the region terms the line states BEFORE choosing a producer. (a) `insideName`: a region/country term that is a proper part of the matched producer's name, as the line writes it (Strategy 1 only), is the name — `matchRegion` searches past it, so "Vega Sicilia Pintia, Toro" still finds Toro; region terms whose name two countries share carry `sharedWith`. (b) Entries whose `normalize()` form differs from the full name keep `full` (`normalize(name, true)`, designators kept and respelled by `spellDesignators`); `placeLike` (from `buildShortNameGuard` — a place or grape, or a preposition before one) means the producer counts only where `full` is written. (c) `namedOnlyInRegions`: a name the line writes only inside longer stated region names is the region's. (d) `tokenOverlap` returns 0 when every shared token is one of the line's region words. None of these change confidence numbers for a producer the line does name — Strategy 1 scoring is untouched
- Varietal names in wineUnified are combined ("Syrah / Shiraz") — the indexes split them into separately matchable aliases and include varietalLookup synonyms; producer terms index "&"/"et"/"and" conjunction variants
- dnaEvolution.test.js and countryAttribution.test.js inline mirrors of production logic (ESM/JSON-import constraints) — if you change matching logic in matchEngine/wineResolver, update the mirrors; sommPicks.js is dependency-free specifically so its tests hit the real module. The core-name alias rules and the short-name guard are mirrored ONCE, in `__tests__/helpers/producerAliasesMirror.js` (both suites build their indexes from it); countryAttribution's two mirror locks fail the moment it and `producerAliases.js` disagree on any producer
- Supabase browser client (supabase.js) FAILS THE BUILD (throws) when `NEXT_PUBLIC_SUPABASE_*` are absent rather than stubbing silently — the static `/` prerender calls `createClient`, so a misconfigured deploy can't go green with dead auth. Server routes use cookie-based sessions via `@supabase/ssr` (`supabaseRoute.js` for cookie-writing redirects, `createServerClient` with no-op cookies for the session-less keepalive)
- **SSRF: any route that fetches a user-supplied URL MUST go through `safeFetch` (ssrfGuard.js)** — never a raw `fetch()` with `redirect: "follow"`. The guard resolves DNS and rejects private/loopback/link-local/metadata addresses on the initial URL and every redirect hop. `/api/fetch-menu` is the current caller
- wineAutocomplete.json (140KB) lazy-loads on quiz Step 5 only — doesn't affect initial load
- `/api/parse-wine-list` accepts base64 image, PDF, or scraped text; returns `{ wines: [...] }` (Path A: structured JSON → match engine) or `{ rawText }` (Path B: text parser — ONLY when the non-JSON reply reads as a wine list per `looksLikeWineList` in `src/lib/wineListText.js`; Claude sometimes answers a blank or tiny image in prose despite the JSON instruction, and conversational, refusal, or too-little text returns the branded `no_wines` error instead — model prose must never reach the paste box as "Extracted from your photo"). Both converge at `finishReading()` → `analyzeEntries()` / `commitAnalysis()` in `src/app/recommend/MatchList.js`
- API GET routes that must run per-request (like `/api/keepalive`) need `export const dynamic = "force-dynamic"` or Next statically prerenders them into no-ops
- **Next inlines `process.env.NODE_ENV` at compile time** — "development" under `next dev`, "production" in a build (`define-env-plugin.js`) — so a runtime NODE_ENV never reaches route code: `NODE_ENV=test npm run dev` does NOT make server code see "test". Gate test-only server behavior on an explicit env flag (the `E2E_DISABLE_RATE_LIMIT` pattern), never on NODE_ENV=test. And any `next dev` compile re-evaluates server modules, so module-level state (the limiter's Map) resets whenever a page or route compiles — including an entry Next re-compiles after disposing it for ~60s idle. That's why the live-in-e2e limiter throttled only sometimes (mostly on a warm second run)
- **Auth pages read searchParams as a SERVER prop, never `useSearchParams`** — on a statically-served page, useSearchParams suspends during hydration and REMOUNTS the form, wiping typed input. And their submit buttons ship disabled until hydration (`hydrated` state): a pre-hydration click fires a NATIVE form GET submission — full reload, query params dropped, input wiped (and a password-in-URL leak once inputs get `name` attrs). e2e specs wait for the enabled button as their hydration signal before filling
- `ANTHROPIC_API_KEY` is required in Vercel env vars; without it all four Claude routes degrade gracefully (scan errors are friendly, somm and palate-narrative fall back silently). Local `.env.local` carries a key too (added July 29, 2026 — verified live), so Claude paths fully exercise in dev. ## API Usage

The Anthropic API is a core part of this product. Three routes, all using `CLAUDE_MODEL` and sharing the rate limiter + cost logging:

- **Wine list scanning** via `/api/parse-wine-list` — measured ~$0.009/scan (text path; images somewhat higher)
- **Bottle label extraction** via `/api/scan-label`
- **Somm curation** via `/api/somm-picks` — measured $0.021–0.025/curation with feedback-rich payloads (3.4–3.6k in / 0.7–0.9k out tokens, 12–20s)
- **Palate narrative refresh** via `/api/palate-narrative` — regenerates the profile narrative only when the palate genuinely moved (a dna_timeline event, or ≥5 newly rated bottles since `narrative_updated_at`); cookie-session auth via `@supabase/ssr` `createServerClient`; ANY failure silently keeps the existing narrative — measured ~$0.006/regeneration (0.8k in / 0.2k out tokens, ~6s)
- Worst-case engaged session ≈ ≤$0.12
- When adding new API-consuming features, be mindful of cost but don't avoid the Anthropic API — it's approved and encouraged

## What NOT to Do

- Don't add new features before existing ones are stable
- Don't introduce new dependencies without a strong reason
- Don't change the brand voice or visual identity without discussion
- Don't optimize prematurely — get it working, then get it fast
- Don't add new paid API integrations without discussion — Anthropic API is the approved exception
- Don't hardcode Claude model IDs anywhere — use `CLAUDE_MODEL` from anthropicConfig.js
- Don't write outcome-tolerant tests for critical paths — at least one spec must hard-fail when the happy path breaks
